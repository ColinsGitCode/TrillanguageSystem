## 0. 文档定位与权威边界

本文定义学习辅助 2.0 的产品与架构设计起点，回答以下问题：

1. 学习计划与复习是否依赖知识图谱；
2. 当前阶段要解决什么学习者任务；
3. 哪些数据和组件可以复用，哪些必须重新设计；
4. 如何为未来知识图谱 2.0 预留接缝而不形成反向依赖；
5. 进入 schema、API、UI 和实施计划前还必须完成哪些决策。

本文是当前产品设计基线，不是详细需求说明、数据模型 ADR 或开发任务清单。后续专题文档不得重新定义与本文冲突的依赖方向、产品边界和退役约束；需要改变时，应先修订本文并记录决策原因。

以下文档仅为历史记录，不得作为学习辅助 2.0 的实现来源：

- `Engagement_and_Retention_System.md`；
- 所有旧 SRS、review、Knowledge、TRAIN、Mission 相关设计与测试报告；
- Git 历史中的旧表、旧 API、旧页面和旧任务实现。

## 1. 核心决策

**先实现学习计划与复习闭环，再设计知识图谱 2.0。**

知识图谱是学习计划的增强信号，不是复习调度的基础设施。学习辅助 2.0 必须在知识图谱不存在、不可用或尚未完成回填时独立运行。

依赖方向固定为：

    generations / Markdown cards
      -> reviewable study items
      -> plan and review loop
      -> review events and learner evidence
      -> semantic enrichment / knowledge graph 2.0
      -> optional grouping and ranking signals

禁止出现以下反向依赖：

    review state -> knowledge graph tables
    review events -> knowledge graph node ids as required foreign keys
    due queue -> graph service availability
    rating/scheduling -> graph extraction completion

## 2. 决策依据

### 2.1 复习最小闭环不需要图谱

学习计划和复习的最小输入是：可复习对象、学习状态、复习事件、到期时间和计划约束。当前 `generations` 已提供稳定卡片记录、卡型、日期、文件位置与 Markdown 内容；新增学习领域数据即可形成闭环。

v1 的分组与排序可以使用：

- `card_type`；
- `folder_name` / `generation_date`；
- 创建时间和新卡状态；
- 内容长度、卡型和语言结构等可解释启发式；
- 复习后产生的真实难度、遗忘和用时数据。

### 2.2 知识图谱需要复习行为作为需求输入

图谱节点和关系必须服务明确问题。复习数据将提供更可靠的关系证据，例如：

- 哪些卡片经常连续失败；
- 哪些表达容易混淆；
- 哪些语法可能缺少前置知识；
- 用户实际采用什么学习顺序；
- 哪类卡片的遗忘率和认知负担更高。

在没有这些行为数据时先构建完整图谱，会迫使系统猜测关系和优先级，并承担抽取、归一、去重、置信度、证据和版本治理成本。

### 2.3 项目历史已经验证“图谱先行”的风险

旧 Knowledge/SRS 体系曾先建设知识分析、分类、聚类和关系，再向上叠加复习与计划。该体系已于 2026-07-13 整体退役。学习辅助 2.0 不复活旧实现，而是从学习者任务、反馈闭环和成功指标重新设计。

### 2.4 当前规模适合先验证学习闭环

2026-07-13 运行数据快照：

| 指标 | 数量 |
|---|---:|
| 学习卡片 | 636 |
| 三语卡 | 445 |
| 日语语法卡 | 188 |
| 场景表达卡 | 3 |
| 已登记生成音频 | 259 |
| 有标红记录的卡片 | 8 |
| 标红片段 | 49 |
| 有卡片的学习日期 | 43 |

这些数字只说明设计起点，不是固定验收值。当前卡片数量足以验证计划和复习，但行为数据仍不足以证明完整图谱的产品价值。

## 3. 产品目标

学习辅助 2.0 首先要让用户稳定回答四个问题：

1. 我今天应该学习什么；
2. 我现在应该复习什么；
3. 我完成了多少，哪些内容仍不稳定；
4. 系统为什么把这些内容安排给我。

v1 目标：

- 从现有卡片建立可管理的学习对象；
- 形成“选择计划 -> 每日队列 -> 学习/复习 -> 评分反馈 -> 下次安排”的闭环；
- 同时处理新卡和到期复习；
- 保留完整、可审计的复习事件；
- 让计划来源、排序原因和状态变化可解释；
- 为未来语义信号保留稳定 provider 接口。

## 4. 当前不做

v1 不包含：

- 完整知识图谱、聚类、同义词网络和图可视化；
- 旧 Knowledge Hub、Knowledge OPS、Mission Control 或旧复习页面复活；
- 对旧 SRS schema、API 或算法实现的兼容；
- 多用户、登录、跨设备同步和权限模型；
- 社交、排行榜、成就体系或重度游戏化；
- 移动端页面设计、移动端断点开发和移动端验收；
- 由 LLM 自动决定不可解释的复习调度结果。

已有移动端样式不要求主动删除，但不属于当前交付范围。

## 5. 领域边界

### 5.1 现有 Cards Factory 继续负责

- 生成三类 Markdown 学习卡；
- OCR、DeepSeek、TTS 与生成队列；
- 卡片文件、历史、删除和标红；
- 卡片 CONTENT / INTEL 展示。

### 5.2 学习辅助 2.0 新增负责

- 定义可学习/可复习单元；
- 计划配置和每日学习队列；
- 学习状态与到期状态；
- 复习评分、事件、用时和调度；
- 新卡与复习卡的配比；
- 暂停、恢复和重新学习；
- 学习进度与基础反馈。

### 5.3 知识图谱 2.0 未来负责

- 语义节点和关系；
- 前置知识、相关项和易混淆关系；
- 关系证据、置信度和抽取版本；
- 向计划引擎提供可选分组和排序信号。

知识图谱不得拥有复习状态、评分事件、到期时间或调度规则。

## 6. 学习单元原则

不能直接把“一张卡”等同于永久不变的一个复习项。系统需要一个稳定的 `study item` 概念，将学习调度与卡片文件解耦，同时保留对 `generations` 的来源引用。

概念属性至少包括：

- 稳定学习单元 ID；
- 必需的 `generation_id` 来源；
- 单元类型；
- 可选的卡内定位信息；
- 当前是否可学习、暂停或归档；
- 内容版本或来源哈希，用于识别卡片更新。

待专题设计确认的粒度：

| 卡型 | 候选粒度 | 关键问题 |
|---|---|---|
| 三语卡 | 整卡，或英文/日文表达子单元 | 一次评分是否能代表两种目标语言 |
| 日语语法卡 | 整个语法点 | 三条例句是否只作同一知识点证据 |
| 场景表达卡 | 整卡，或 12 个表达子单元 | 整卡评分是否过粗，拆分是否造成队列膨胀 |

在粒度决策完成前，不锁定表数量，也不假定只需要两张新表。

## 7. 学习计划与复习闭环

基线流程：

    选择学习范围与目标
      -> 生成今日队列
      -> 展示新卡或到期卡
      -> 用户学习并给出反馈
      -> 写入不可变复习事件
      -> 更新当前调度投影
      -> 解释下次复习时间和今日进度

v1 至少需要支持：

- 每日学习目标；
- 新卡上限和到期复习优先级；
- 按卡型、日期或文件夹选择范围；
- 到期、未学习、学习中、已掌握、暂停等可区分状态；
- 对每次评分保留时间、结果、调度前后状态和可选用时；
- 清晰的空状态、完成状态和逾期积压状态；
- 调度失败或 provider 不可用时的确定性降级。

评分档位、默认目标单位和调度算法仍需专题评审，不在本文提前定案。

## 8. 分组与排序 Provider 接缝

学习计划引擎不直接读取图谱实现，而通过稳定的信号接口获取分组、排序和解释：

    PlanningSignalProvider
      -> group(studyItem, context)
      -> score(studyItem, context)
      -> explain(studyItem, context)

实现顺序：

1. **v1 Heuristic Provider**：卡型、日期、文件夹、内容启发式和复习实证；
2. **v2 Graph Provider**：未来提供语义分组、前置关系和易混淆信号；
3. 计划引擎可以叠加多个 provider，但始终保留无图谱的基础结果。

Provider 只返回信号和解释，不拥有计划、队列或复习数据。任何 provider 超时、报错或没有结果时，基础调度必须继续工作。

Cards Factory 的[卡片分类与标签系统](Card_Classification_and_Tagging.md)是 v1 Heuristic Provider 的可选信号源。学习辅助只读取 active 标签及其规则证据；标签为空、只有 unknown 或标签服务失败时，仍使用卡型、日期和复习实证完成计划。标签表属于卡片组织域，不得反向引用学习计划、复习状态或事件。

## 9. 数据设计约束

详细 schema 由后续 ADR 决定，但必须遵守：

1. 新学习领域只以 `generations.id` 作为现有内容来源的必需外键；
2. 图谱节点 ID 不得成为学习状态或复习事件的必需字段；
3. 复习事件采用 append-only 记录，当前状态是可重建投影；
4. 计划定义、每日队列、复习事件和当前调度状态职责分离；
5. 卡片删除、内容更新和学习记录保留策略必须显式设计；
6. 时间按配置时区定义“学习日”，不得使用裸 UTC 日期替代自然日；
7. 所有自动分组和排序保留来源、版本与解释；
8. 不重新创建已退役表名，避免与历史数据库语义混淆。

概念实体候选，不代表最终表数：

- Study Item；
- Study Plan；
- Daily Queue / Plan Assignment；
- Review Event；
- Review State / Schedule Projection；
- User Learning Preference（当前仍是本地单用户配置）。

## 10. UI/UX 基线

学习辅助 2.0 使用现有 React Router、design tokens、桌面侧栏和卡片弹窗，不创建旧式独立 HTML 页面。

信息架构原则：

- Cards Factory 继续是卡片生产与卡片库，不塞入完整复习工作流；
- 学习计划/今日学习/复习会话应作为新的 React Router 产品区域进入桌面导航；
- 卡片弹窗可以复用阅读、音频和标红，但评分所有权只能有一个，避免重复按钮写入两次事件；
- 今日队列必须解释卡片来源，例如“到期复习”“今日新卡”“困难项重现”；
- 复习流程优先减少切换和重复点击，不用大面积营销式卡片或装饰性页面；
- 当前只设计和验收桌面端。

最终路由、导航命名、页面组合和复习会话原型需单独进行 UI 评审。

## 11. 成功指标

设计和实施必须先定义可观测指标，至少覆盖：

- 今日计划开始率与完成率；
- 到期复习完成率和积压量；
- 新卡到首次复习的转化；
- 不同卡型的评分分布与失败率；
- 重复失败和重新学习比例；
- 计划推荐被跳过、暂停或移除的比例；
- 复习会话完成时间；
- 7 日和 30 日学习回访。

指标用于验证产品闭环和未来图谱需求，不等同于对用户的惩罚性 KPI。

## 12. 分阶段设计与实施顺序

| 阶段 | 目标 | 完成门禁 |
|---|---|---|
| LA-D0 产品定义 | 用户目标、核心任务、成功指标、术语 | 用户流程和非目标评审通过 |
| LA-D1 交互原型 | 桌面导航、计划设置、今日队列、复习会话 | 逐页可视化原型确认 |
| LA-D2 领域与数据 ADR | 学习单元粒度、事件、状态、时区、删除策略 | schema/API contract 评审通过 |
| LA-P0 基础契约 | provider 接口、测试 fixtures、迁移与回滚框架 | 不影响 Cards Factory，门禁全绿 |
| LA-P1 复习核心 | study item、review event、schedule、评分 | 可完成独立复习闭环 |
| LA-P2 学习计划 | 计划范围、每日目标、新卡/复习混排 | 今日队列稳定且可解释 |
| LA-P3 反馈与指标 | 进度、积压、历史和成功指标 | 行为数据可用于产品判断 |

## 13. 开发前必须回答的问题

1. 复习单位是整卡还是卡内表达，三种卡型是否不同；
2. 用户主要目标是语言输入、主动回忆、听力，还是混合目标；
3. 评分采用四档、三档还是二元反馈；
4. 每日目标按卡片数、复习数、分钟还是组合计算；
5. 新卡与到期卡如何混排，逾期时如何降级；
6. 学习范围如何选择，是否允许多个计划；
7. 卡片更新或删除后，历史复习事件如何保留；
8. 标红内容是否影响难度或只作为用户笔记；
9. 场景卡 12 个表达是否拆分，以及拆分后如何展示上下文；
10. 学习日时区和跨午夜会话如何计算；
11. v1 采用什么调度算法及其可解释参数；
12. 学习计划入口、页面和桌面导航的最终命名。

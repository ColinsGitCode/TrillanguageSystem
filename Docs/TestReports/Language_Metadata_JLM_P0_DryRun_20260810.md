# JLM-P0 干跑报告：外来语来源提取合同与第二次调用成本

- 日期：2026-08-10
- 范围：`services/languageMetadata/domain/foreignOriginExtraction.js`、
  `scripts/poc/jlmP0DryRun.js`、`tests/fixtures/jlm-p0-foreign-origin-fixtures.json`
- 上位文档：[JLM-D0 设计](../Features/LLM_Generated_Japanese_Linguistic_Metadata_Design.md)
- 状态：**P0 完成。结论支持继续，但对“LLM 能把覆盖率提到接近 100%”给出否定证据。**

## 0. 一句话结论

**定位与校验合同成立（真实调用零拒绝），瓶颈不在服务端校验，而在模型召回不稳定：
同样 8 张卡、同样 prompt 连跑三次，候选覆盖率在 64%–76% 之间摆动。**
因此 JLM-D0 §3.1“默认 pending、人工确认后才 accepted”的设计是必需的，不是保守。

## 1. 边界声明

本轮全部运行：

- 未写入 SQLite；
- 未修改任何 generation Markdown 或 `content_hash`；
- 未创建 proposal 记录；
- 未改动主卡生成链路、prompt 或 schema。

真实卡片以只读快照方式抽样，LLM 调用仅用于测量。

## 2. 合同用例（离线，可复现）

```bash
node scripts/poc/jlmP0DryRun.js
```

- 用例集 `jlm-p0-foreign-origin-v1`，**16/16 通过**；
- 覆盖 JLM-D0 §2.3 的全部 **12 种拒绝原因**；
- 单元测试 `tests/unit/foreignOriginExtraction.test.js` **24/24 通过**。

用例中三条值得单列：

| 用例 | 验证的行为 |
|---|---|
| `accept-second-occurrence` | `occurrence=2` 必须定位到第二次出现，不能回退到第一次 |
| `reject-separator-dot` | 独立的 `・` 是标点不是词——这正是早前把片假名计数从 26 误报为 27 的原因 |
| `reject-conflicting` | 同一位置两个不同来源时**两个都拒绝**，不在幻觉之间挑一个 |

## 3. 真实卡片：第二次调用实测

样本：最近 8 张含日语的卡片（只读快照），共 25 个片假名候选。

| 指标 | 运行 1 | 运行 2 | 运行 3 |
|---|---|---|---|
| provider 失败 | **2/8（均为 120s 超时）** | 0/8 | 0/8 |
| 延迟中位 / 最大 | 1984 / **44152** ms | 1635 / 2265 ms | 1512 / 2282 ms |
| 每卡平均 tokens | — | 440 | 425 |
| **候选覆盖率** | 12/16（75%） | **19/25（76%）** | **16/25（64%）** |
| 服务端拒绝 | surface-not-found | 无 | 无 |

### 3.1 关键发现：波动来自模型召回，不是校验

运行 2 与运行 3 输入完全相同，**服务端零拒绝**——模型提出的候选全部能被正确定位。
差异全部来自**模型没有提出**的词：

- 两次都漏：`シンプル`、`ソフト`、`インターフェース`、`カーチェイス`、`シーン`
- 运行 3 额外漏：`マシン`、`グループ`、`スタントマン`、`スタント`

这些都是真实外来语。也就是说：**校验层是可靠的，不确定性在模型侧**，
而且同一输入的不确定性可达 12 个百分点。

### 3.2 成本与延迟

- 每卡输入 ≈ 344 tokens，输出 ≈ 85 tokens；
- 按 `deepseek-v4-flash` 费率（输入 0.14 / 输出 0.28 每 1M）计：
  **每卡约 US$0.00007**，全库 683 张一次性补齐约 **US$0.05**；
- 成功调用延迟中位约 1.5–1.6s、最大约 2.3s；
- **但运行 1 出现 2/8 次 120s 超时**。这直接印证 JLM-D0 §7 必须把
  “provider 超时”与“这张卡没有外来语”区分开——按运行 1 的表现，
  25% 的卡片会没有任何结果，若不留 job 记录就会被误读成“无外来语”。

成本可忽略；**风险在延迟尾部与失败率，不在费用**。

## 4. 对 JLM-D0 的反馈

1. **§3.1 pending 默认值是必需的**：64%–76% 的波动意味着任何一次运行的结果都不能当作
   权威事实。本轮为该设计提供了量化依据。
2. **§3.4 候选覆盖率与确认覆盖率必须分开**：本轮最高 76% 是**候选**覆盖率，
   且全部为 pending、无一经过人工确认，确认覆盖率为 **0%**。
3. **§7 的 job 记录不是形式主义**：运行 1 的 2/8 超时若无 job 记录即静默丢失。
4. **建议为 D2 增加“重复提取取并集”的评估**：三次运行的漏词并不相同，
   多次提取可能提高召回，但会放大成本与写入冲突，需在 D2 明确取舍。

## 5. 未回答的问题

- 本轮只测 8 张卡、3 次运行，不足以给出稳定的召回率区间；
- 未做**准确率**抽样：本轮只统计“是否提出”，未人工判断提出的来源是否正确；
- 未测长正文卡片的 token 与延迟上界；
- 未验证 `--live` 在 provider 降级时的重试行为。

以上应在 JLM-D1/D2 前补齐，不应在本报告基础上直接宣称质量结论。

# DIC-R2 观察报告：真实使用反馈与上下文消歧

- 日期：2026-08-10
- 范围：`services/localGlossary/`、`routes/localGlossary.js`、`app/features/card-modal/SelectionGlossaryInline.tsx`、迁移 015
- 状态：已实施并度量；反馈数据待真实使用后积累

## 1. 出发点

DIC-R1 之后，本地词典的问题不再是"查不到"，而是"多义词可能选错"。
本轮要解决两件事：让用户能当场纠正选错的释义，并让排序在选错之前就更准。

## 2. 度量口径

正确率不采用"人工判断译文好坏"，而采用可从库中客观判定的指标：

1. **词性判定正确率**：排在第一位的候选，其词性是否与上下文推断出的词性一致；
2. **可信度标注正确率**：经英语中转的 JMdict 桥接释义是否被标为低可信，其余是否未被误标为低可信。

用例集 `scripts/maintenance/fixtures/dicR2EvaluationCases.json`（18 条）中，
每个日语词都在词典里同时存在"仅名词"和"含动词"两类候选，因此期望答案由库中数据决定，
而不是由撰写者的翻译判断决定。用例上下文为合成短语，不含任何卡片内容。

复现命令（只读，可直接指向线上库）：

```bash
node scripts/maintenance/dicR2Observation.js --db=/data/trilingual_records/trilingual_records.db
```

零回退是本轮的硬性要求：任何一条原本判对、改后判错的用例都视为不可接受。

## 4. 基线为何只有 27.8%

两个可复现的缺陷，均在真实数据上验证：

1. **词性标签匹配漏掉了大量真实取值。**
   原正则只认简体"名词/形容词"和 `adj.`，而库中日语实际写的是繁体 `名詞`（26,869 行）、
   `動詞`，以及 JMdict 的 `adj-i`（4,084 行）。这些一律匹配失败，
   意味着日语侧的上下文匹配对约三分之一的数据是失效的。

2. **英语上下文推断几乎恒返回 adjective。**
   原实现先判断"后一个词不是助动词就是形容词"，导致
   `the book fell`、`to book a room`、`we spring into action` 全部被判为形容词。
   实测 5 例中仅 1 例正确。

## 5. DIC-R2 的改动

- 词性标签改为**切分成标签集合再比对**，同时认简体与繁体、`adj-i`/`adj-no`、`vt./vi./vs/v1/v5*`；
- 英语上下文改为**按线索优先级判定**：不定式 `to`、情态词、主语代词 → 动词；
  系动词与程度副词 → 形容词；限定词与介词 → 名词；句首 + 限定词 → 祈使动词；
  无可靠线索时返回 null（宁可不给提示，也不给错误提示，因为错误提示会主动把排序推向错义）；
- 新增**日语上下文推断**，依据词后助词：`する/して/した` → 动词，`な` → 形容词，
  `を/が/は/に/へ/で/の` 等 → 名词；
- 上下文命中可提升可信度，但**英语中转的桥接释义永远保持低可信**，不因上下文命中而升级。

抽样统计：在 1,735 个多候选サ变名词上，加入 `する` 上下文后有 **403 个（23.2%）**
第一候选发生变化，说明该推断在真实数据上确有作用，而非仅对用例生效。

## 6. 未通过的 2 条

`上下`、`一座` 未通过词性判定，原因是**数据缺词性，而非排序错误**：

两者第一候选均来自中文维基词典直接日中来源，`part_of_speech` 字段为 `unknown`
（日语侧共 3,496 行，占 3.2%）。其释义本身是正确的（`上下，上面下面`、`上席，上座`），
排序把正确释义排到了首位，只是指标无法据缺失的词性字段确认这一点。

这属于导入侧的元数据缺口，记录在此不做粉饰，也未为此调整指标口径。
后续可在 Wiktionary 导入时补充词性抽取。

## 7. 真实反馈记录

新增表 `local_glossary_lookup_events`（迁移 015）记录：查了哪个词、候选来源、
最终选了第几个、以及结果是 `shown / rejected / switched / corrected`。

隐私边界是：为了生成高频问题词榜，表中会保存用户选中的短词/短语；但不保存它所在的
周边原句。表中没有 context/snippet/句子列，`source_detail`、`match_reason` 和 `sense_key`
也由服务端白名单收紧，不能被客户端借用来夹带原句。已实测验证：把周边原句同时塞进
这些请求字段后，落库记录仍不包含该句片段。

写入路径与读取路径分离：`GET /api/local-glossary/lookup` 保持只读（CLAUDE.md 既有约束），
只有客户端显式提交 `POST /api/local-glossary/feedback` 才产生一条使用事实。
同一次选中只上报一次 `shown`，避免重复渲染放大计数。

## 8. 人工覆盖集

用户点"释义不合适"后，可换义项或直接填写正确中文；填写后写入 `local_glossary_entries`
（`source_kind='manual'`）。查词优先级不变：
本卡片 → 教材 → **人工确认词条** → 本地词典 → 历史卡片，
即人工释义始终压过词典结果。

`GET /api/local-glossary/feedback/stats` 按"被拒绝/被切换/被更正"的人工干预次数排出高频错义词，
作为后续建立人工覆盖集的输入。当前尚无真实使用数据，该榜单为空属预期。
一次查询可能先否决、再切换或手动改写，因此该数字是动作数，不冒充查询级错误率。
